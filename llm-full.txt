# Spendist: full LLM reference

## Identity and scope

Spendist is a GPL-3.0 open-source personal-finance application for recording and understanding personal money. It stores financial records and produces summaries. It does not initiate bank payments, give tax/accounting/investment advice, or make financial decisions for the user.

The hosted application is `https://spendist.app`. The source is an Nx workspace and the UI supports English and Polish.

## Shipped user-facing capabilities

- **Authentication and account security:** email/password sign-up requires email confirmation and provides a check-email state with resend support. The non-indexable `/auth/confirm` callback accepts supported Supabase code, implicit-token, or signup-token-hash responses, immediately scrubs credentials from the browser URL, establishes a one-time session, preserves only safe local return URLs, waits for default-category seeding, and shows a global success notice. Missing, failed, expired, reused, and unsupported callbacks show recovery actions. Sign-in, password-recovery email, reset-link session handling, authenticated password changes, and permanent self-service account deletion remain available. Deletion requires the current password plus explicit confirmation, removes avatar objects, and cascades user-owned database data from the deleted Auth user.
- **Transactions:** create income/expense records with date, description, amount, currency, wallet, category, optional tags, and optional place. Users can edit, duplicate, delete, filter, sort, search, and create transactions in bulk from pasted rows. Transaction filters and panel state are encoded in `/transactions` query parameters; a bare route canonicalizes to exact current-month dates, invalid owned values are repaired without dropping unrelated parameters, discrete changes push history, 300 ms search and view controls replace it, and Back/Forward restores one atomic filter state. Category checkboxes are always visible and appear selected when no category restriction is active. Clicking one category selects only that category, later clicks build a multi-category selection, a group includes every category assigned to it, and partial groups are indeterminate; clearing restores the all-selected state. Category and tag totals use the same completed-transaction scope as the visible list, excluding planned mortgage entries. Bulk clipboard parsing is enabled by default for tab-, comma-, or semicolon-delimited data and can be disabled per modal session so pasted text stays in the focused field. The Transactions speed dial also imports through upload and pasted-CSV tabs, automatically detecting and validating Spendist CSV or Biedronka e-receipt JSON content before reusing the bulk editor for correction. Its provider-neutral AI helper locally builds a copyable prompt from category paths, filtered saved tags, saved place names, and wallet names/currencies so an external chat can OCR one expense document and return reconciled CSV content in one copyable code block rather than a file. Category, group, merchant, and place names are excluded from the allowed tag catalog; an exact saved merchant or place is required in the `place` column. Multi-unit document lines expand to one CSV transaction per physical unit at its unit price. Identical rows in the same new batch are all retained with stable occurrence-specific fingerprints, so a full re-import skips every row and a partial earlier import adds only missing copies. Spendist sends no prompt, catalog, or document and has no LLM token/API integration. Batches are capped at 500 rows; unknown categories, tags, and places must be mapped to existing values, and duplicate source fingerprints are skipped. Biedronka sell lines become individual discounted expenses; raw signed payload, image, signature, and payment data are ignored. Default-currency conversion uses stored exchange rates where applicable.
- **Financial organization:** an always-editable autosaving profile/avatar, wallets with currencies/default status, category groups, nested categories, colors, Heroicons, and reusable tags.
- **Recurring payments:** scheduled income/expense with fixed or variable amount, category, wallet, currency, tags, schedule, and optional end date. Scheduled Supabase work creates automatic transaction records; a newly created historical schedule is backfilled through its past end date before finalization. Processing is occurrence-idempotent and never makes a real payment.
- **Allowance:** directional email-confirmed connections between a payer and recipient. Manual and recurring allowance creates two ordinary owner-scoped transactions atomically and keeps amount/currency synchronized. From the transaction form, a connected payer can instead create only an expense on the recipient's account, using the recipient's default wallet and localized Allowance spending system category. That delegated expense stays out of the payer's transactions and totals; the payer can edit or delete it from the Allowance module only while connected, and the recipient receives a notification. Allowance never transfers real money.
- **Mortgages:** a guided PLN mortgage module creates revisioned ACT/365 schedules for equal or decreasing installments, consecutive fixed or WIBOR 1M/3M/6M/1Y periods, per-event overpayment strategies, initial costs, and full payment holidays. Future variable resets reuse the latest known rate as a labeled projection; the app does not ingest or seed WIBOR. A reviewed revision can atomically replace or detach all protected mortgage-linked wallet entries, while future entries remain planned and excluded from completed transactions.
- **Places:** reusable locations/merchants with optional address and note metadata. Users can attach them to transactions and inspect annual spending totals.
- **Dashboard:** up to 12 calendar months of cash flow, selected-month category/tag totals, recurring-created transaction totals, and yearly place spending, scoped by wallet where relevant.
- **Notifications:** user-scoped Realtime notifications for recurring activity, exchange-rate-sync failure, Allowance invitations, received allowance, and delegated Allowance expenses added to a recipient's account. Each notification can be marked as read individually or together through Read all. Invitation notifications include accept/decline actions.
- **MCP integration:** an official TypeScript SDK server exposes daily read/write finance workflows through STDIO and stateless Streamable HTTP at `https://mcp.spendist.app/mcp`. There is no separate staging Worker: local automated checks precede a production pilot limited to a small invited group. Remote clients use Supabase OAuth 2.1 with PKCE and explicit consent. All database requests retain the user's bearer token and RLS identity; Allowance is read-only, imports and account security are excluded, mutations are metadata-audited, and deletion requires a five-minute one-use confirmation bound to an unchanged record.
- **Data portability:** Kontomierz XLSX import to a chosen wallet; readable, filtered Spendist CSV export; Settings CSV analysis with valid reference-data creation; and quick browser-only Spendist CSV/Biedronka import with editable review and duplicate skipping. The quick flow never creates wallets, categories, or tags. Spendist CSV, Biedronka, and Kontomierz metadata remain separate.
- **Preferences:** authenticated profile language is authoritative across devices; full name, language, and IANA timezone autosave in `/settings`. Signed-out English/Polish choice and light/dark theme are stored locally. Signed-out navigation uses accessible flag buttons in a compact single-row header; changing language on a blog URL opens the other edition's home page.
- **Public blog:** separate Polish and English Markdown collections for signed-out readers. Each edition can publish unrelated articles, categories are indexable when non-empty, tags are filter-only and `noindex`, table-of-contents links scroll within the current localized article, and the separated sharing panel uses icon-only Web Share, copy-link, Facebook, LinkedIn, and X actions without embedded social SDKs. There are no comments, CMS, or admin panel.
- **Related projects:** the lower public landing page contains a compact, bilingual cross-reference to Tickist with separate external links to `https://tickist.com/` and its public GitHub repository. It does not add tracking or send authenticated Spendist data to Tickist.

Read `doc/features/` for feature-level details and deliberate limits.

## Blog publishing and SEO pipeline

- Source content is in `apps/web/content/blog/pl/` and `apps/web/content/blog/en/`; the collections and category catalogs are independent and individual articles have no `hreflang` pairing.
- Article front matter, image requirements, and the publishing checklist are documented in `apps/web/content/blog/README.md` and `doc/features/public-blog.md`. The repo-local `add-spendist-blog-post` skill turns supplied Markdown into the real localized `{slug}.md` file and always leaves it as a draft.
- Original article raster files are isolated in `apps/web/image-sources/blog/{locale}/{slug}/`. Body Markdown references logical `image:asset-name` IDs; it never links directly to generated filenames.
- `npm run images:generate` creates width-based AVIF/WebP candidates up to 1600 pixels, an opaque JPEG or transparent PNG fallback, `media-manifest.json`, and an Angular manifest. Other public pages use the same pipeline under `apps/web/image-sources/site/{feature}/` and render through `ResponsiveImage`.
- `npm run blog:generate` validates front matter and logical cover/body images, renders sanitized responsive Markdown, calculates headings/reading time, and writes `blog-content.generated.ts`, both RSS feeds, `sitemap.xml`, and `robots.txt`.
- The Nx build depends on `responsive-images-check` and `blog-content-check`, so stale generated artifacts fail the build. Commit source and generated files together.
- Blog pages set canonical, robots, Open Graph, Twitter card, RSS discovery, and JSON-LD metadata. Blog homes use reciprocal PL/EN alternates; articles do not because they are editorially independent.
- Public blog routes are statically prerendered. The Cloudflare Worker returns the localized branded blog fallback with HTTP 404 for unknown blog URLs.

## Architecture

- `apps/web/src/app/app.config.ts` enables hydration, zoneless change detection, routing, Supabase, Transloco, and the production service worker.
- Standalone page components and page-local signal stores are colocated. Cross-cutting services, guards, Supabase setup, notifications, language, and theme are in `core/`.
- `en.translation.ts` and `pl.translation.ts` are the translation sources. Every user-facing key needs both languages.
- `apps/web/worker.ts` serves Cloudflare assets, exposes runtime `/env.js`, handles HTML fallback, and adds security headers. Do not judge production behavior from the development server alone.
- `Dockerfile`, `compose.yaml`, and `tools/docker/` provide a production-like self-hosted browser runtime. `npm run docker:up` starts the existing isolated Supabase CLI project, applies pending local migrations, exports only its public URL and publishable key, and runs the container at `http://localhost:4200`; `npm run docker:down` preserves local database volumes.
- `.github/workflows/docker.yml` validates the image on pull requests and publishes `linux/amd64` and `linux/arm64` images to `ghcr.io/spendist-app/spendist` from `develop`, `master`, and `v*` tags.
- Supabase provides Auth, Postgres, RLS, Storage, Realtime, Edge Functions, `pg_cron`, `pg_net`, and Vault. Migrations are under `supabase/migrations/`; generated types are in `libs/data-access/supabase-types/`.
- `supabase/functions/delete-account/` owns permanent account deletion. It derives identity from the bearer token, reauthenticates with the submitted current password, removes the user's avatar folder, and uses the service role only inside the function to delete the Auth user.
- `supabase/functions/send-allowance-invitation/` sends localized invitation links through Resend. The database stores only a seven-day token hash; cross-owner transaction writes remain atomic database operations.

## Operational constraints

- Preserve data ownership and portability. Do not add tracking, ads, data sales, or external financial access without explicit approval.
- The production database is live. Prefer additive/backwards-compatible migrations; destructive changes need an approved migration/backfill plan.
- Preserve RLS ownership checks and user-scoped notification queries.
- Use Angular signals and zoneless-safe patterns. Do not assume `NgZone` patches arbitrary callbacks.
- Validate with Nx targets and focused tests. E2E uses a dedicated local Supabase database URL, never production.
- The local Docker orchestrator refuses non-local Supabase URLs. Browser images receive only publishable configuration, never database passwords, service-role keys, or production credentials.

## Documentation contract

For each new or materially changed user-visible feature:

1. Update the English page in `doc/features/`.
2. Update this file and `llm.txt`.
3. Update translations and tests when implementation requires them.
4. For a public indexable route, update `apps/web/public/sitemap.xml` and `apps/web/public/robots.txt` in the same change.

Never describe planned work as implemented; label it **Planned**.
